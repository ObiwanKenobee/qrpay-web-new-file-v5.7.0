# ADR 0014: Provenance verifier consistency hardening

- **Status:** Proposed
- **Date:** 2026-11-14
- **Decision owners:** Sanctum Scan maintainers
- **Depends on:** ADR 0012 (participant provenance export), ADR 0013 (offline provenance verification)

## Context

M013 introduced an offline verifier that recomputes the M012 manifest digest and checks evidence, revision and reassessment relationships. A digest match alone does not establish that the exported fields form a structurally coherent record. A document can be re-serialized and supplied with a newly calculated digest, so the verifier must also reject internally contradictory projections and malformed relationship values without assuming the manifest was signed.

The first verifier validated revision order and key digests, but did not fully compare the exported current attestation projection to its source statement or latest revision. Some nested review fields and loosely cast prior-version values were also under-validated.

## Decision

Strengthen schema-1.0.0 verification without changing the export format, API endpoints, database schema or financial workflows.

The verifier will:

1. Require a recognized platform review state. A pending review carries no completed-review digest; a completed review must include a valid digest equal to the evidence digest, plus non-empty method, summary and review timestamp.
2. Validate original attestation snapshot fields and revision snapshot fields needed to explain the current effective statement.
3. Recompute the expected current attestation projection from the original attestation when no revisions exist, or from the final revision when revisions exist. Status, version, scope, method, outcome, basis summary and recorded timestamp must agree.
4. Validate reassessment prior-version values as positive integers before using them, require version 1 to have no revision ID, require later versions to identify a positive revision ID, restrict prior status to supported values, and reject self-references.
5. Require non-empty event/message type, actor and timestamp fields and reject duplicate event/message IDs within their respective collections.

Malformed or inconsistent exports fail closed with validation errors. The verifier remains read-only and offline.

## Consequences

- Consumers receive stronger structural and cross-field consistency checks for the existing schema.
- Exports generated by the M012 serializer remain the compatibility target; no endpoint or schema version change is intended.
- Unit coverage now includes current-projection mismatches, incomplete completed-review records and malformed prior-version values.
- No network access, cryptographic signing, trusted timestamp, exporter authentication, source-file byte inspection or factual adjudication is introduced.
- This does not change exchange, dispute, payment, wallet, refund or settlement state.

## Validation

Tests are authored in `tests/Unit/SanctumScan/ProvenanceManifestVerifierTest.php` and remain subject to PHP lint and PHPUnit execution. The GitHub Actions runner-provisioning issue affecting M009–M013 remains an independent validation blocker; no test pass is claimed until the workflow actually executes.
